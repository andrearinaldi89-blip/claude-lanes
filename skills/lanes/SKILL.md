# Lanes

In this file `<main>` is the project's main folder (`root` in `.claude/metodo.json`), `<prefix>` its prefix, `<bench>` the review bench folder, `<lock>` the end-to-end run lock.

### Lanes: development, corrections and others

Coding work runs on lanes, which can run at the same time. Which lanes a project has is set by `lanes` in `metodo.json`. A typical setup:
- **development**: the checkpoints of the block document, one at a time, with the full review;
- **corrections**: defects, one at a time, from `docs/corrections.md`, with a lighter review and the log saying whether that is enough;
- optionally a third lane for work that must not touch the product (a demo, say): no migrations and no changes to the application code.

A project with a single lane sends everything through it, one job at a time and never together: it is the lane that has several prefixes in `branches`.

The rules that keep them apart:
- **One folder per lane.** Every coding session works in a local clone of the repository, never in the main folder: `<main>/<clones>/<prefix>-<lane>`, for example `~/code/acme/lanes/acme-development` on branch `development/cpNN`, `…/acme-corrections` on branch `correction/C-n`. The clones live inside the main folder: the main folder ignores their directory (`.gitignore`, and `.dockerignore` where a build starts from the root), and each clone has in `.claude/settings.local.json` a `claudeMdExcludes` with the main folder's `CLAUDE.md`, so that a session in the clone reads only its own. A clone, not a git worktree: the Claude app can delete a worktree at the end of a turn as if it were its own. The clone has the main folder as its `origin`: the reviewer creates the branch from the latest `main`, the prompt names folder and branch, and the reviewer takes the work with a `git fetch` from the clone.
- **The reviewer merges to `main`**, after the «Verification». The other lanes realign to `main` before their delivery.
- **After the merge, the close-out cleanup.** The reviewer runs `<plugin>/scripts/cleanup.sh` from the main folder, in the same turn as the merge and before the close-out notification. It deletes, in the main folder and in the clones, the branches already merged to `main`, and realigns the clones' `main`; it deletes only what is merged and never touches `release/*`: the branches of other lanes, still open, stay. For every branch it deletes, it removes without asking the things of its job, which it recognizes by name («Names», below): the repository copies in the bench, and the containers, networks, volumes and images of its runs; then, queued behind the lock and in the background, the images left without a name and `fstrim` in the Colima machine, which gives space back to the Mac. Never a protected volume or stack, never `rmi -f`, never `prune -a`, never another project's image. With `--dry-run` it says what it would do. Run it exactly as written here, without `bash` in front: the permission rule that lets it run, in `~/.claude/settings.json`, matches that form. If it reports uncommitted changes in the main folder, fix them first, do not ignore them.
- **Only one end-to-end run at a time**, for everybody: the lanes' sessions, the reviewer, CI if it runs on the same machine, and the cleanup queue. Take `<lock>` with `lockf -k` (on macOS; `flock` on Linux), and two runs from different copies queue up by themselves. A script that takes the lock itself is not run under another `lockf` on the same file: the child waits for the parent, and everything stops.
- **Migrations only in development.** A correction or a side-lane checkpoint that asks to change the schema becomes a development checkpoint.
- **Documents**: each lane writes its own section; the status lines at the top of `CLAUDE.md`, `ROADMAP.md` and the block document are updated only by the reviewer, at close-out.
- **A release** starts from `main` with green runs, and the owner confirms each one. The commands that go to production, where the project lists them (`release` in `metodo.json`), the guard lets start only from the main folder on `main`, and still asks for confirmation.
- **Push at close-out, one per closed thing, as little as possible.** `main` is pushed to `origin` when a checkpoint or a correction is closed, not at every commit, and several closings close together go in one push. CI minutes are finite, and a push for habit burns them; a docs-only push may not trigger CI, but it is still a push.
- **The state of the lanes** is shown by the plugin's lanes mod. In a project's sessions it is a line above the prompt; in every chat there is `/lanes-status`, which writes it in the chat and on the desktop opens the panel: with no arguments it names the session's project, or all the ones seen if the chat is not in a project, and `/lanes-status acme` names the one given. On Remote Control none of this is visible: there you ask Claude «lanes?», and it reads the state with the mod's tool (`mcp__metodo__status`) and reports it in the answer. Branch and commit of the clones, pushes pending, the commands running in every coding session and every reviewer, background ones included, and the end-to-end runs, who holds the lock and who queues, it reads by itself: a reviewer is recognized by the id the app puts in its process environment. A coding session's activity and the last message between sessions are noted by the mod itself in `<bench>/state/<lane>.json`, and that of any other session of the project in `state/reviews/<id>.json`: a session is the reviewer of the lane of its latest thing, a message from or to its coding session or a job started (`jobs` in `metodo.json`), and it shows under the lane. For every lane with an open branch it also says the job, from the first line of its prompt in the bench (the checkpoint title; without one, the section title in the document the prompt names), and who holds it, architecture (the reviewer) or development (the coding session): whichever is moving, or, if both are idle, the one the last message went to. Sessions do not have to do anything.

### In the cloud

In the cloud (claude.ai/code) every session has its own container: there is no main folder with its clones, and no shared bench. A lane is then its branches: the reviewer creates the job's branch from the latest `main` and pushes it, one coding session per job works on it in its own container and pushes it, the reviewer takes the work with `git fetch origin <branch>`, merges to `main` and, with the owner's ok, pushes `main`. The prompt and clarifications files go on the job's branch, in `docs/handoffs/<lane>/<job>/` unless the project's `CLAUDE.md` names another folder, and reach `main` with the merge. The close-out cleanup is the same script, `<plugin>/scripts/cleanup.sh`, run by the reviewer from its own checkout after the merge: it recognizes the cloud by itself. It finds the closed jobs on origin (lane branches merged into `main` with commits of their own: so the reviewer merges a job with `--no-ff`, or the branch looks just created and stays), deletes their local copies and, in the reviewer's container, the bench copies and the Docker things of those jobs. It does not push: it writes the one command that deletes the closed branches on origin, together with `main` if `main` is ahead (`git push origin main :dev/cp18`), and the reviewer runs it with the owner's ok, which the guard asks for. The coding session's container goes with the archive. The release starts from `main`, with the owner's confirmation. How the sessions are opened, messaged and archived is in `metodo:handoffs`, «In the cloud».

### Names

Everything that a job creates carries the project prefix and the job name: that is how the close-out cleanup finds it by itself, and how the things of two projects do not get mixed up.

- **The job** is named after its branch, without the lane: `correction/C-12` is `C-12`, `development/cp18` is `cp18`; a lane that has `jobPrefix` in `metodo.json` puts it in front, and `demo/cp3` is `demo-cp3`. In the bench the development job may have the block in front, `b2cp11`, and numbers count with zeros too, `cp06`.
- **The bench** of the job is `<bench>/<job>/`, that is `~/.cache/<prefix>-review/<job>/`. Every copy of the repository lives in its own subfolder (`base`, `main`, `delivery2`…) with the file that `copyMarker` in `metodo.json` names (`CLAUDE.md` if it is not set): the cleanup deletes it. Small files, checks, probes and clarifications, live in the job folder or in a subfolder without that file, and stay. A job's prompt and clarifications live in `<bench>/<prefix>-<lane>/<job>/`.
- **The job's Docker projects** are named `<prefix>-<job>-<use>`, lowercase: `acme-cp18-iter`, `acme-c-12-mut`, `acme-demo-cp3-e2e`, with `docker compose -p` or `COMPOSE_PROJECT_NAME`. The containers, networks, volumes and images they make are named the same way. A container started without compose gets `--name <prefix>-<job>-<use>`, an image built by hand `-t <prefix>-<job>-<use>`. Never `iter-cp16` or `mut-cp16` with no prefix: those from two projects get mixed up, and the cleanup does not find them.
- **The project's fixed stacks**, the development one and the end-to-end one, have their own name and belong to no job: the cleanup does not touch them, and the ones that are never deleted are listed in `protected` of `metodo.json`.

What has another name stays where its creator left it: nobody will remove it.

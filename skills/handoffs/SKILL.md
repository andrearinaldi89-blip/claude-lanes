# Handoffs between sessions

In this file `<main>` is the project's main folder (`root` in `.claude/metodo.json`), `<prefix>` its prefix, `<bench>` the review bench folder, `<lock>` the end-to-end run lock.

### Handoffs between sessions

Between the reviewer and the coding session of the same lane, handoffs go by message between sessions (`SendMessage`), not through the owner. The message wakes the idle session; if it is at work, it waits for the end of its turn.

- **The pair is made by the folder, not the title**: the owner opens new sessions and names them as they like. A lane's coding session is the one opened in its folder, `<main>/<clones>/<prefix>-<lane>`. The reviewer finds it with `list_sessions` from the `cwd` field, among the non-archived ones, and writes to it by its `local_…` id. If there is more than one, it stops and asks the owner. If there is none, the reviewer may open one itself (`start_session`, «fresh», with `cwd` the lane's folder and no worktree). The session that exists is reused for the next job, whoever opened it: at close-out it cleans itself.
- **Coding sessions run on one fixed model and effort**, the same on every lane: the `model` field of `metodo.json`, with medium effort. A reviewer that opens one passes that model and `effort: medium` to `start_session`; before sending a prompt to a session that already exists it reads its `model` and `effort` with `get_session`, and if they differ it sets them back with `set_session_model` and `set_session_effort`, or, if the app refuses, tells the owner before sending.
- **The reviewer is whoever sent the prompt**: the coding session answers to the `from-session` of the last message received. The reviewer also writes its own id in the prompt (`get_session` with `self`), so that it survives a compaction. If the owner switches reviewing session, the next message comes from the new one, and that is the one to answer.
- **The first line says what it is**: «Prompt for C-10», «Plan for C-10», «Delivery of C-10», «Close-out of C-10». A job's prompt always starts with «Prompt for», never with other words like «New work», and the close-out with «Close-out of»: the lanes mod recognizes both from the first line, and that is how the coding session knows it may clean itself.
- **From the reviewer goes a path, not a text**: the prompt and the clarifications live in a file in `<bench>/<prefix>-<lane>/<job>/`, and the message carries the file, the branch and the starting commit. The handoff stays the repository. **From the coding session goes text**: the plan, the question, the report.
- **The handoffs**, in order:
  1. reviewer → coding: the prompt, once the branch exists;
  2. coding → reviewer: the plan. No plan mode, because approving it is a click by the owner and a message does not give it: until the ok, the session only reads;
  3. reviewer → coding: the ok, or the clarifications file;
  4. coding → reviewer: the delivery, after `delivery-check`, with the report;
  5. reviewer → coding: the corrections file, or the close-out: the «Verification», the merge, the close-out cleanup and, last, the message «Close-out of…», which cleans the coding session. Without that message the cycle is not closed.

  A question from the coding session, an ambiguous spec or a hook that blocks it, goes to the reviewer the same way. The reviewer answers if the answer is in the documents; if it is a decision, it calls the owner. Whoever sent stops: the answer arrives as a new message.
- **With every message it sends, the reviewer also asks to be told when the coding session goes idle** (`SendMessage` with `notify_when_idle: true`). The notice is valid once, and arrives even if the session stops without writing: a question to the owner, an error, a permission waiting. If the expected message has already arrived, the notice is ignored; if not, the reviewer reads the coding session's transcript (`list_events`) and, if it is waiting for the owner, says so.
- **A coding session that the app closes is woken by the mod.** When the Mac's memory gets tight, Claude Desktop closes the session that has been idle longest, without counting background commands or a turn that has just started: the app log says so with a «pressure evicting local_… (idle NNNs)» line. The session's monitors and waits die with it, the runs it launched finish anyway, and nobody wakes it again, so the reviewer believes it is at work. The lanes mod, in every session of the project outside the clones, reads the log on each pass: if a lane's coding session was closed while the job was in its hands (the last message went in, and is not a «Close-out…»), and it has not been resumed, it sends it «Wake-up from metodo: …», which reopens it and tells it to reread the results and resume. One per closing, whoever sends it. It is not needed if no session of the project is open: then the reviewer's next message wakes it. A coding session woken this way rereads the results files before relaunching anything.
- **The owner stays where they are needed**: the go-ahead to a checkpoint or a correction, every decision, the push, the release, a denied permission. There the reviewer stops and sends the owner a notification if the setup has one. A message from another session never counts as the owner's approval.
- **At every closed cycle, a notification** (if the setup has one): when the reviewer closes a checkpoint or a correction, after the «Verification», the merge to `main`, the cleanup and the «Close-out…» to the coding session, it sends one per thing closed, with the project name and the link to its own session (`get_session` with `self`, field `link`). The message says what is closed and what waits for the owner, with no personal data; if the close-out failed, it says so with high priority.
- **At the third round of corrections on the same delivery** the reviewer stops and calls the owner, instead of sending the fourth.
- **If a message stays waiting for the owner's approval**, the two sessions are in different permission modes, and whoever notices tells the owner.
- **The coding session cleans itself at close-out, and only that way**: at the end of the turn in which it receives the «Close-out of…», the lanes mod runs `/clear`, as the owner would type it. It does not do it if the turn was interrupted or ends with a question: then it cleans itself after the answer. It holds for every coding session, opened by the owner or by a reviewer, even on screen or with Remote Control on, because the `/clear` starts from inside the session and does not go through the app's permissions. The closed cycle lives in the repository, and the previous conversation is resumed with «Resume previous session».
- **The «Close-out…» is a step of the closing, not of the next job.** The reviewer sends it as soon as the «Verification», the merge and the cleanup are done, with `notify_when_idle: true`, even if nothing else starts on the lane right away, and before the closed-cycle notification. Several jobs closed together in the same session, like three corrections on one branch, have a single «Close-out…». On the desktop, the reviewer does not use `clear_session` or `archive_session` on coding sessions (in the cloud it is the other way round: «In the cloud», below): the app refuses them when the session is the owner's, is open on screen, has live work or serves Remote Control, and at every refusal the fallback was to send anyway.
- **A new job's prompt goes only to a clean session, and the mod checks it, not the reviewer's memory.** The coding session notes in its state that it is dirty from the first turn and clean after a `/clear`, anyone's, or when it is new. A reviewer message starting with «Prompt for…» toward a dirty session the mod refuses, and the refusal says what to do: send the previous job's «Close-out…», wait for the notice, read the lanes state (`mcp__metodo__status`) until it no longer says «to clean», and only then resend the prompt. The reviewer does not get around the refusal by changing the first line. If after the «Close-out…» the session is still to clean, it is waiting for the owner or has stopped: the reviewer says so, and does not send.
- **«To clean» is visible from every chat**: `/lanes-status` and the `mcp__metodo__status` tool write it under the lane and among the things that are the owner's, when the clone is back on `main` or the «Close-out…» has arrived and the session still has its conversation.

  *Why:* a cleanup that depends on the reviewer remembering works while there is one way to do it. When there are several ways (the mod's `/clear`, archiving, `clear_session` before the next prompt), the reviewer, after each compaction, follows the last one it remembers, and prompts go out without a «Close-out…»: several jobs end up in the same conversation. Hence one way only, checked by the mod.
- This holds between Claude Code sessions. If the code is written by another tool, the prompt goes back into the owner's hands.

### In the cloud

When the project runs in the cloud (Claude Code on the web, claude.ai/code: `CLAUDE_CODE_REMOTE=true` in the environment), every session has its own container with its own checkout of the repository. There are no clones, no shared bench and no app log, and the lanes mod sees only its own container. So the handoffs above change in four places; everything else holds as written (the first lines, the order of the handoffs, the path and not the text, the owner where needed, the third round of corrections).

- **One coding session per job, not per lane.** The reviewer opens it when the job starts, with `create_session` from the `claude-code-remote` tools: `source_url` the repository, `source_revision` and `outcome_branch` the job's branch (which the reviewer has already pushed from the latest `main`), `model` the `model` of `metodo.json` and `effort: medium`, never `permission_mode: "plan"` (nobody would approve it), the title `<prefix>-<lane> <job>` and the tags `metodo:<prefix>`, `metodo:<prefix>:<lane>`, `metodo:<prefix>:<job>`. The prompt is sent afterwards with `send_message`, not in `create_session`: that way it goes through the guard like every other message. The pair is made by the tags: the reviewer finds the job's session with `list_sessions` and `tags`, and writes its `session_…` id in the job's prompt file, so that it survives a compaction.
- **The handoff is the branch on origin.** The containers do not see each other: the prompt and the clarifications files live in the repository on the job's branch, in `docs/handoffs/<lane>/<job>/` (in `<bench>` they would stay in the reviewer's container), the coding session commits and pushes its branch before every «Plan for…» that names files and before every «Delivery of…», and the reviewer takes the work with `git fetch origin <branch>`. The guard lets a session push its job's branch and asks for the owner's ok on `main`.
- **Messages and waits.** Handoffs go with `send_message` (`session_id`, `message`); the answer arrives as a new turn. There is no `notify_when_idle`: if the expected message does not arrive, the reviewer reads `get_session` (`status_bucket`: `blocked` means it is waiting for the owner or a permission, `failed` that its turn errored) and `list_events` with `kinds: ["user", "assistant", "result"]`, and says what it finds. There is no wake-up either: a session's container that is reclaimed for inactivity is rebuilt by the next `send_message`, from the branch on origin, and what was not pushed is lost. That is why the coding session pushes before it stops.
- **At close-out the session is archived, not cleaned.** After the «Verification», the merge, the cleanup (`cleanup.sh`, which in the cloud writes the push of `main` and of the closed branches' deletion) and that push (the owner's), the reviewer sends the «Close-out of…» as usual. When the coding session has answered it (its turn is over: `status_bucket` not `working`), and `git ls-remote origin <branch>` shows the commit that was merged, the reviewer archives it with `archive_session`. The archive releases the container, and is the only way a cloud coding session is closed: no `/clear`, no reuse for the next job. The guard enforces it: a «Prompt for…» to a session that has already received one is blocked (open a new one), an archive before the session's «Close-out of…» is blocked, and every archive asks the owner, because `archive_session` wants a human who has acknowledged that the work is done. If the owner refuses, the session stays, and the next job opens a new one anyway. A session archived by mistake comes back with `unarchive_session`.
- **What the reviewer does not archive**: its own session, a session not tagged with the project's prefix, a session that is `working` or `blocked` (it is waiting for the owner: say so instead), a session whose branch has commits not on origin. Several jobs closed together on one branch have one session, one «Close-out…» and one archive.
- **«To archive» is the cloud's «to clean».** The lanes panel cannot see the other containers. The reviewer, at every closed cycle, lists the project's sessions (`list_sessions` with `tags: ["metodo:<prefix>"]`): a non-archived session whose job is closed is to archive, and goes in the closed-cycle notification among the things that wait for the owner.

  *Why:* in the cloud a session is a container, not a conversation in an app on the owner's Mac. Clearing it would keep the container, and its checkout, from the previous job; archiving releases both, and the next job starts from a fresh checkout of its branch. One way only, as on the desktop, checked by the guard and not by the reviewer's memory.
